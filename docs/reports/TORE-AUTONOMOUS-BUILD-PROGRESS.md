### 1. Wrong-law/same-article-number adversarial testing (citation grounding)
- Traced the full citation retrieval path (`parse-exact-citation-query.ts` → `canonical-law-titles.ts` → `knowledge-legal-corpus-retriever.ts`'s `lookupVerifiedHits`). Found that only 5 laws are canonically disambiguated by `lawId`; every other law relies on a loose `title.includes(hint)` substring check, which a same-prefix law (e.g. a law and its own "...-ийг дагаж мөрдөх журмын тухай хууль" enactment statute) can satisfy.
- Attempted a stricter title-match fix twice (word-boundary-only, then word-boundary-plus-trailing-"хууль"-requirement); **both were reverted** after they broke 3-4 pre-existing tests that rely on this codebase's deliberately loose matching (e.g. a fixture titled "Барилгын тухай" with no trailing "хууль" at all). A correct fix would need corpus-level law-id backing beyond the 5 canonical laws — not done this phase; documented as a known, not-yet-fixed limitation.
- Added a **new, safe regression test** (`tests/unit/knowledge-legal-corpus-retriever.test.ts`) proving the one case that IS already handled safely: when two legally distinct, title-overlapping laws BOTH have the cited article number, the system returns CONFLICT rather than guessing — never silently picks one. Added a second regression test for the existing "official-title boilerplate prefix" case (no regression).
- Added a general-purpose word-boundary-aware title-matching helper (`titleContainsTerm`, `article-search.ts`) and applied it to the SQL/in-memory pre-filter's `titleTerms`/`excludeTitleTerms` checks — a narrow, safe hardening (candidate pre-filter only, not the final decision gate) that blocks a different, real class of mismatch (a canonical law's full title, e.g. "ЭРҮҮГИЙН ХУУЛЬ", wrongly matching a longer title via Mongolian case-suffix agglutination, e.g. "...ХУУЛИЙГ...").
- Added 5 new tests (`tests/unit/detect-exact-citation.test.ts`) documenting malformed/ambiguous citation parsing: a comma-separated article list is correctly NOT treated as one exact citation (falls through to open-question search); a chained cross-reference ("article X гэж заасны дагуу law 2's article Y") resolves the second law via a contaminated-but-still-correct title hint for canonical laws (documented, not fixed, as a non-canonical-law gap that fails safe — never found, not a wrong-law risk); empty/whitespace input never crashes; a bare article number with no law name is never an exact citation; a syntactically valid but nonexistent article number (e.g. "0") is accepted by parsing but safely refused at retrieval (no fabrication).

### 4. Real browser testing — a genuine crash found and fixed
- Started the local dev server (`.env.local`'s `DATABASE_URL` confirmed `127.0.0.1:5432` before starting) and drove the actual `/legal-ai` chat composer with Claude in Chrome.
- **Confirmed, again, that `resize_window` does not change `window.innerWidth`** (stayed at the real 3440px monitor width for every requested size). No other device-emulation tool exists in this environment, and the app has no JS-driven responsive logic (grep for `innerWidth`/`matchMedia`/`useMediaQuery` in `src/components/legal-ai` and `src/app` returned nothing) to substitute with an automated unit test either. **No mobile/tablet visual verification was performed or should be assumed** — same honestly-reported limitation as before.
- **Found a real, reproducible crash**: typing a moderately long message (~140 characters) into the composer via rapid automated keystrokes twice reliably triggered React's "Maximum update depth exceeded" error, visibly breaking the composer (dev overlay, sometimes clearing the draft). A literal one-shot value-set (simulating a real OS paste) did **not** reproduce it — this is specifically about many rapid, discrete keystroke-driven re-renders, not message length or content.
- Root-caused via `npm run lint`, which (independently of the browser finding) flagged `spellcheck-textarea.tsx:151` — `useEffect(() => setActiveKey(null), [value])` — as "calling setState synchronously within an effect can trigger cascading renders," a pre-existing error already present in the lint baseline before this session.
- **Fixed**: removed the effect. It's unnecessary — `activeIndex` already re-derives from the current `ranges` every render, so a stale `activeKey` naturally stops matching once an edit shifts span offsets, without an explicit reset. (A `useRef`-comparison replacement following React's own documented "adjust state during render" pattern was tried first and rejected: this repo's lint config forbids reading/writing a ref during render too, so it would have traded one lint error for two new ones.)
- **Verified the fix** three ways: (a) `npx eslint` on the file now shows 3 errors (was 4) — only the pre-existing, unrelated `anchor` useMemo ref-access findings remain, zero new ones introduced; (b) all 28 existing `spellcheck-textarea-*.test.tsx`/`.ts` tests still pass unchanged; (c) re-ran the exact same browser repro twice (the English sentence and the original Mongolian paragraph) against the fixed build — no crash, no console error, orthography underlines rendered correctly.
- Conversation switching (New chat while a draft was in progress) was also exercised in the browser and worked cleanly — composer reset, no stale draft, no console error.

### 3. Upload queue: audited against reality, not the briefed premise
- **The brief described "a three-at-a-time image upload queue and three-worker OCR pool."** Neither exists. `src/components/legal-ai/use-document-upload-queue.ts` is a deliberately **strictly serial** queue (one upload at a time — documented reason: the first upload creates the conversation, later ones must see that id, so parallel uploads would split one thread across conversations). `src/infrastructure/ai/tesseract-ocr-engine.ts` maintains exactly **one** reused worker, not a pool. This is reported as fact, not assumed from the premise.
- Zero prior test coverage existed for the upload queue's own ordering/cancellation/retry logic. Added `tests/unit/use-document-upload-queue.test.ts` (11 tests, real hook via `@testing-library/react`, no mocked internals): 1/3/5-file serial ordering, settle() across the full chain, partial failure + retry, removing a queued (not yet started) attachment vs. cancelling an actively-uploading one, `reset()` on conversation switch aborting every in-flight upload.
- **Real bug found and fixed:** `addFiles()` had no duplicate-file detection — selecting or dropping the same file twice queued two independent uploads. Fixed with a same-batch dedup guard (exact match on name+size+lastModified; a file re-added after removal is unaffected, since it's no longer in the live item list). Not a billing risk — entitlement consumption is architecturally tied to starting a question thread, confirmed by reading `legal-ai.service.ts`, completely independent of attachment count.
- OCR timeout (`OCR_TIMEOUT_MS`, `withOcrTimeout`, worker reset on timeout) was already covered by `tests/unit/ocr-engine.test.ts` — not re-tested.
