# TORE — Git синк болон архитектурын тойм (2026-09-08)

## 1. Товч дүгнэлт

- Таны компьютер дээрх **`tore`** болон **`tore-legal-data-engine`** repo-уудыг GitHub-тай синк хийж, тодорхойгүй байдлыг арилгав.
- `tore` нь төлөвлөж байснаас хамаагүй том, идэвхтэй хөгжиж буй код суурьтай: **859 TS/TSX файл, ~199,000 мөр код, 127 тестийн файл**. Зөвхөн MVP биш, Legal AI, зөв бичгийн шалгагч, TORE Student академи, QPay төлбөр зэрэг олон feature production дээр ажиллаж байна.
- Хамгийн чухал **архитектурын эрсдэл**: хуулийн эх сурвалж боловсруулах логик **хоёр тусдаа системд хуваагдсан** байна (доор дэлгэрэнгүй). Энэ бол цаашид хамгийн түрүүнд шийдэх ёстой асуудал гэж үзэж байна.
- Docs (`docs/README.md`)-ийн дагуу албан ёсны дараагийн алхам нь **Sprint 2.2 Identity implementation** — blueprint бэлэн, эхлүүлэх зөвшөөрөл хүлээж байна.

## 2. Git синк — юу хийсэн

### tore
- **Асуудал байсан:** local `main` нь GitHub-с **37 commit хоцорсон**, мөн **1 commit push хийгдээгүй** (зөв бичгийн шалгагчийн false-positive засвар) байсан тул шууд ажиллах боломжгүй байлаа.
- **498 файлын "өөрчлөлт"** нь бодит контент биш, line-ending (CRLF/LF) зөрүү байсан тул цэвэрлэв.
- GitHub-ийн сүүлийн 37 commit-ийг авч, local commit-ийг үүн дээр `rebase` хийхэд `src/domain/mongolian-orthography/dictionary.ts` болон `suggestions.ts`-д **бодит зөрчил** гарсан:
  - GitHub дээрх хувилбар нь зөв бичгийн толь бичгийг **`legal-lexicon.ts`** гэсэн тусдаа модуль болгож, morphology-based (дагаварт суурилсан) танилтаар сольсон, mэдэгдэхгүй үг таамаглах fuzzy-matching-ийг **бүрмөсөн унтраасан** байв (яг таны commit-ийн зорилготой ижил төрлийн алдаа — "нөхөн→хэрхэн" мэтийн буруу санал — засах зорилготой).
  - Гэвч энэ шинэ хувилбарт **тээврийн хэрэг/согтуугаар жолоодох хэргийн тусгай үгс** (жолооч, тээврийн хэрэгсэл, согтууруулах, амьсгал, спирт, агууламж) болон **газар зүйн нэрс** (Өмнөговь, Ханбогд, Цогтцэций) орхигдсон байсан тул эдгээрийг `legal-lexicon.ts`-д нэмж, шинэ (илүү сайн) архитектурыг хадгалсаар таны тодорхой хэргийн засварыг бүрэн хадгалав.
- **Үр дүн:** `main` одоо GitHub-тэй бүрэн синк, ажлын хавтас цэвэр, `git status` цэвэр. TypeScript compile шалгалт (`tsc --noEmit`) миний засварласан 3 файлд алдаагүй.
- **Танд хийх зүйл үлдсэн:** энэ 1 commit-ийг `git push` хийх (би энэ орчноос GitHub рүү бичих эрхгүй тул push хийгээгүй). Мөн `npm install` ажиллуулах шаардлагатай — учир нь GitHub дээрх шинэ commit-үүд `nspell`, `dictionary-mn` (жинхэнэ Монгол Hunspell толь) гэсэн шинэ dependency нэмсэн бөгөөд таны локал `node_modules`-д одоохондоо алга.

### tore-legal-data-engine
- Commit-ийн хувьд GitHub-тэй яг синк байсан. Зөвхөн 4 файлын line-ending noise байсныг цэвэрлэв. Өөр зүйл хийх шаардлагагүй байсан.

## 3. `tore` — код/архитектурын тойм

Clean Architecture давхаргууд (`domain → application → infrastructure → presentation`) тодорхой дагагдсан, `docs/`-д тусгасан загвартай нийцэж байна:

- **`src/app`** — Next.js App Router: client/lawyer/admin dashboard, `/legal-ai`, `/student`, marketplace route бүгд бий.
- **`src/domain`, `src/application`, `src/infrastructure`** — стандарт давхаргажилт, ports/adapters загвар зөв хэрэгжсэн (жишээ нь `HttpLegalCorpusRetriever` нь `tore-legal-data-engine`-тэй HTTP-ээр холбогддог, зөв adapter байдлаар).
- **Auth:** Auth.js v5, edge/node тусдаа config (стандарт Next.js practice), `middleware.ts` route guard-тай.
- **Төлбөр:** QPay gateway бүрэн хэрэгжсэн (`qpay-http-gateway.ts`, callback route).
- **Тест:** 127 файл — сайн хэмжээ, гэхдээ 199k мөрөнд харьцангуй цөөхөн ч байж болно (chi нарийн coverage report-той харьцуулаагүй).

### Гол эрсдэл: хоёр тусдаа "хуулийн эх сурвалж" систем

`tore` дотор **`src/engine/`** гэсэн том, бие даасан дэд систем байна (`knowledge/crawler`, `knowledge/parser`, `retrieval`, `citation`, `reasoning`, `doctrine` гэх мэт — legalinfo.mn болон шүүхийн (shuukh) эх сурвалжаас мэдээлэл татаж, боловсруулдаг өөрийн бүрэн pipeline). Үүнээс гадна repo-ийн үндсэн `scripts/` хавтсанд `ingest-legalinfo-*.ts`, `discover-legalinfo.ts` гэсэн legalinfo.mn ingest script-ууд бас бий.

Үүний зэрэгцээ, тусдаа **`tore-legal-data-engine`** microservice яг ижил зорилготой — legalinfo.mn-с хууль татах, архивлах, эшлэл баталгаажуулах, версийг хянах — ажлыг зориулалтын, цэвэр hexagonal architecture-тай системээр хийхээр зохион байгуулагдсан.

**Асуудал:** Master Architecture баримт бичигт (`docs/20-tore-master-architecture-v1.md`) `legal-data-engine` гэдэг үг **нэг ч удаа дурдагдаагүй**. Өөрөөр хэлбэл эдгээр хоёр системийн хоорондын харилцаа (аль нь эцсийн эх сурвалж мөн, аль нь хуучирсан/шилжилтийн процесст байгаа) албан ёсоор шийдэгдээгүй байна. `tore`-ийн `HttpLegalCorpusRetriever` client үнэхээр legal-data-engine рүү хандаж байгаа нь сайн шинж боловч `src/engine/knowledge/crawler` болон root-ийн `scripts/ingest-legalinfo-*` идэвхтэй ашиглагдсаар байвал:
- Хоёр дахин ажил хийгдэж, засвар хоёр газар зэрэг хийгдэх эрсдэлтэй
- Хуулийн текстийн эх сурвалж/хувилбар хоёр системд ялгаатай байх (нэг өөрчлөгдөж, нөгөө нь өөрчлөгдөхгүй) эрсдэлтэй — энэ нь **хуулийн платформд онцгой чухал** (буруу/хуучирсан хуулийн заалт харуулах эрсдэл).

## 4. `tore-legal-data-engine` — тойм

Илүү жижиг, цэвэр код суурь (79 файл, ~6,100 мөр, 18 тест). README-д бичсэн Phase 1-3 төлөвлөгөөнөөс илүү ахисан байдалтай — `src/application/ingest`, `src/parsers/legalinfo`, `src/application/evaluation` гэх мэт бодит ingest/parse/evaluate код аль хэдийн байна (README дээрх "Phase 1 = foundation only, no crawl" гэснээс цааш явсан). Architecture зөв, ганцхан commit ("feat: build legal data engine corpus pipeline") дотор их ажил багтсан тул commit history нь хараахан sprint-ээр задарч бичигдээгүй.

## 5. Өрсөлдөгчидтэй харьцуулах, зах зээлийн байрлал (эхний ажиглалт)

Таны зорилго — Harvey.ai шиг, legaldata.mn шиг, гэхдээ өөрийн онцлогтой, ашиг олох, зах зээлд ялгарах платформ. Одоогийн код суурь дараах давуу талтай:

- **Хос талт marketplace + AI хослол** — цэвэр Legal AI (Harvey.ai маягийн) биш, харин хуульчтай холбох marketplace дээр AI нэмсэн нь legaldata.mn (мэдээллийн сан) болон Harvey (зөвхөн AI tool, хуульч холболтгүй) хоёроос ялгарах бодит боломж.
- **Монгол хэлний native зөв бичгийн шалгагч + хуулийн лексикон** — өрсөлдөгчид байхгүй, өвөрмөц онцлог болж чадна.
- **TORE Student академи** — хуулийн боловсрол/сурталчилгаа гэсэн "олон нийтийг соён гэгээрүүлэх" зорилготой нийцнэ.

**Хамгийн том эрсдэл** нь дээрх architecture-ийн давхардал: хэрэв эх сурвалжийн найдвартай байдал (citation accuracy) алдагдвал энэ нь хуулийн платформын хувьд итгэлийг бүрмөсөн алдах эрсдэлтэй тул legal-data-engine-ийг цорын ганц эх сурвалж болгож нэгтгэх нь Sprint 2.2-оос ч түрүүлж авч үзэх ёстой асуудал байж магадгүй.

## 6. Санал болгож буй дараагийн алхмууд

1. **Шийдвэр хэрэгтэй:** `src/engine` (хуучин) vs `tore-legal-data-engine` (шинэ) — алийг нь цаашид эцсийн эх сурвалж болгох вэ? Энэ бол код бичихээс өмнө шийдэх ёстой стратегийн асуулт.
2. **`npm install`** орон нутагт ажиллуулж, шинэ Hunspell dependency-г татах (эсвэл надад дараагийн ээлжинд cloud орчинд бэлтгүүлж болно).
3. **`git push`** хийж commit-оо GitHub-д бичих.
4. Дараа нь: **Sprint 2.2 Identity** эсвэл **engine нэгтгэлийн** аль нэгээр ажлаа эхлүүлэх.

Юуг эхлээд хийхийг тодорхойлвол би тэр даруй эхлэх бэлэн байна.
